ValIO's user-facing messages exist in four locales. The configuration
file itself stays English: keys like `language`, `outputPath`,
`namespace`, `transports` are part of the public API surface and never
get translated — only what ValIO prints to the user (CLI logs, UI
labels, error messages) shifts to the chosen language.

## Switching the UI culture

```bash
valio --lang en generate ...     # English (default)
valio --lang ru generate ...     # Русский
valio --lang de generate ...     # Deutsch
valio --lang zh-cn generate ...  # 简体中文
```

The CLI also honors the `VALIO_LANG` environment variable
(see [Environment variables](/configuration/env-vars/)).

## Where translations live

Each `.resx` file in `src/ValIO.Localization/Resources/` defines one
namespace of strings:

| File                       | Used by                                       |
|----------------------------|-----------------------------------------------|
| `GenerationStrings.resx`   | Orchestrator status messages.                 |
| `ParserStrings.resx`       | OpenAPI parser errors.                        |
| `ValidationStrings.resx`   | Configuration validation errors.              |
| `ConfigurationStrings.resx`| Config loader errors.                         |
| `PluginStrings.resx`       | Generator plugin descriptions (UI tooltips).  |

Each base file (`*.resx`) ships English text. Per-locale overrides live
alongside it as `*.{ru,de,zh-CN}.resx`. Missing keys fall back to the
English value, so adding a new locale doesn't have to be complete on
day one.

## Web and Desktop

The Web UI exposes a language switcher in the top-right menu that
sets a cookie and reloads the page. The Desktop app has a Settings
page entry; the choice persists to
`%APPDATA%/ValIO/desktop-settings.json` (or
`~/.config/ValIO/desktop-settings.json` on non-Windows). Both
front-ends consume the same resx assemblies as the CLI.
